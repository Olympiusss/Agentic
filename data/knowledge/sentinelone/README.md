# SentinelOne knowledge artifacts

Grounded world model for the connected SentinelOne tenant, built per `Sentry_AgenticSOC_Build_Brief_for_Claude.md`. Everything here is derived from live tool calls against the tenant, never invented. Layout:

| Path | Populated by | Contents |
|---|---|---|

| `environment_map.yaml` | Milestone 1 (populated) | What exists in the tenant: hierarchy, endpoints, policies, alerts/storylines, vulnerabilities/applications, optional modules, the Deep Visibility profile, enums, and the tool used per item. Generated by `scripts/discover_sentinelone_environment.py` (`python scripts/discover_sentinelone_environment.py --confirm-dv`, rerunnable). Two real gaps found and recorded honestly rather than fabricated: this tenant's `sentinelone` MCP server has no dedicated tool for endpoint-protection policies at all, and no distinct "Threats" tool (threat questions route to Alerts — see `mcp_tools.md`). |

`purple_ai()` was re-checked live on 2026-07-30 for Milestone 6: still down, now returning an `AuthZ error` from the SentinelOne backend rather than the earlier generic outage message. The hand-composed-PowerQuery workaround and `experimental` gating from Milestone 5 remain in force; re-check before any future DV work per the standing direction.

**Milestone 7 real finding:** re-sampling 50 real alerts (vs. Milestone 1's 5-item discovery sample) found `alert_severity`/`alert_status`/`alert_analyst_verdict`/`alert_classification` all badly undercounted — e.g. severity had only `INFO` recorded, but the real tenant also has `LOW`/`MEDIUM`/`HIGH`/`CRITICAL`. `ontology/sentinelone_ontology.yaml` and `environment_map.yaml` were corrected with the fuller, still-not-proven-exhaustive real distribution. Also corrected: 6 coverage-matrix rows (`host_lookup`, `storyline_pivot`, `agent_health`, `cve_traversal`, `threat_detail`, `vulnerability_general`) whose `status` field was stale at `recipe_drafted`/`validated` even though their bound recipes have carried `status: stable` since Milestone 4 — bumped to `stable` to match, since that field is what Milestone 7's refusal gate (and Milestone 8's harness) actually checks.

**Milestone 8 (test harness and acceptance) closes Phase 2.** `tests/sentinelone_coverage_harness.py` (+ pytest wrapper `tests/test_sentinelone_coverage_matrix.py`) runs one real question per coverage-matrix row against the live tenant, scored on source/traceability/grounding/accuracy. Result: 12/12 (100%), gap-closing 5/5 (100%), Milestone 0's regression fixture passing all 5 literal criteria. Full report: `coverage_matrix/accuracy_report.md`. Two real misses found and fixed before this run: `format_grounding_line()` said "Tenant:" instead of the protocol's actual "Client:" label, and the harness's own `sentry_internal` assertion checked a phrase that was never in the real gate response. Per the brief, this is the last milestone of this phase — the next brief covers agent capabilities.

**Post-Phase-2, third pass: Purple AI replaced, chat UX cleaned up.** Live use
surfaced a batch of real issues: a self-inflicted latency regression (the
router's embedding inference was blocking the asyncio event loop --
fixed with `asyncio.to_thread`), a `threat_count` answer that said "alert"
when the user asked "threat" (fixed — body now says "threat(s)", `Source:
SentinelOne Alerts` still states the honest real system name), and — the
big one — a real DV-hunt question ("find file downloads ending in .zip/.iso/.html")
made the model visibly retry a confirmed-permanently-dead `purple_ai()` in
a loop, burning tokens and ending in a wrong "the tool has limitations"
message. `dv_hunt` went from `not_started`/permanently-refused to `stable`:
the coverage matrix's examples were broadened, 5 new hand-composed MITRE-tagged
templates were added to `dv_cookbook/` (plus 1 extended) from a user-supplied
set of real SentinelOne query examples — each live-probed in its own isolated
connection before being written down — bringing the cookbook to 11 templates
across 3 new hunt_pattern categories (`impact`/`discovery`/`defense_evasion`,
added to `data/schemas/dv_template.schema.json`'s enum). `services/sentinelone_recipe_executor.py`
now does a two-level match for `dv_hunt`: the router confirms the question is
hunt-shaped, then a second embedding match against the retrieval store
(`source="dv_hunt_template"`) picks the specific template, which runs
directly via `powerquery()` — `purple_ai()` is never called. Every dv_hunt
answer states its hand-composed, not-Purple-AI-verified provenance rather
than presenting it as equally authoritative. Also: the grounding line was
simplified to `Source: · Client:` only (Window/Results dropped as redundant
with the natural-language body — confirmed product decision), and the
hardcoded "[Processing tools...]" narration was removed. Harness re-run
after all of this: 13/13 (100%), gap-closing still 5/5.

**Post-Phase-2, second pass: two real production bugs found via live use, fixed.**
First real end-to-end use in the chat UI surfaced two gaps the offline harness
never would have: (1) "how many threats has occurred in the last 24hrs?" was
silently treated as unwindowed (386, "all time") because time-window
extraction only recognized whole days/weeks/months, not hours -- fixed by
generalizing `extract_window_days` to `extract_time_window`, returning the
exact `get_timestamp_range` kwarg name (`hours`/`days`/`weeks`/`months`),
live-confirmed `get_timestamp_range(hours=24)` works identically to
`days=N`. (2) "what about endpoints?" (a natural follow-up to a threat-count
question) was misrouted to `host_lookup`, which demands a specific hostname
and can't answer an aggregate count -- there was no question_class for a
bare endpoint/asset total at all. Added `endpoint_count` (13th coverage-matrix
row, 8th recipe): confirmed live that neither `search_inventory_items` nor
`list_inventory_items` expose a total-count field distinct from the returned
page (`pagination` is always `{}` regardless of limit), so the recipe fetches
at the max limit (1000) and counts `len(data)`, honestly reported as a lower
bound if the page comes back full. Getting `endpoint_count`'s example
questions to not bleed into `host_lookup`'s (both share heavy "endpoint"
vocabulary) took two rounds of tuning -- see `scripts/validate_sentinelone_router.py`'s
updated `KNOWN_AMBIGUOUS_PARAPHRASE_PLAUSIBLE_CLASSES`. Harness re-run after:
13/13 (100%), gap-closing still 5/5.

**Post-Phase-2: wired into live chat.** All of the above was validated by `tests/sentinelone_coverage_harness.py` against a standalone MCP session, but was not reachable by a real user until this pass. `services/sentinelone_recipe_executor.py` (production ports of the harness's 7 stable-recipe executors, calling the live app's `services/mcp_client.py` instead of a standalone script session) and `services/sentinelone_entity_extraction.py` (deterministic, extract-or-ask parameter resolution for a real user's free text — no LLM sub-call) now sit between `services/claude_service.py`'s `chat_stream` and the model: SentinelOne-shaped questions are routed, gated, and answered deterministically before the model ever sees them; only a router `fallback` (low-confidence) decision reaches the model's normal tool-calling turn. See the interception block at the top of `chat_stream`'s try body.

Each of `ontology/`, `coverage_matrix/`, `recipes/`, and `dv_cookbook/` is populated milestone by milestone, each requiring its own acceptance check before starting, per the build brief's sequencing rule. Do not hand-author content into these ahead of the milestone that's supposed to generate it from real tenant data. `routing/`, `retrieval_store/`, and `interpretation/` are the exception: they're build artifacts/runtime logs, regenerated on demand, not milestone-sequenced knowledge.
