# SentinelOne MCP tool inventory (`sentinelone` server, `purple-mcp` v0.7.0)

Generated from a live MCP handshake (`initialize` → `list_tools`) against the connected tenant, not from upstream docs or assumption. 33 tools confirmed present. Two (`powerquery`, `get_timestamp_range`) were additionally exercised with a real `call_tool` and returned live data; the rest have a captured schema but have not yet been called against real data in this tenant — treat their exact runtime behavior as unverified until a recipe (Milestone 4) exercises them.

## Critical corrections to brief assumptions

- **This server exposes "Alerts," not "Threats."** `Sentry_Agent_Task_Execution.md`'s intent taxonomy assumes a "SentinelOne Threats" module distinct from Deep Visibility and from Sentry's internal findings. The actual live tool surface has no `threat`-named tool at all — only `get_alert` / `list_alerts` / `search_alerts`, backed by a GraphQL cursor-paginated Alerts model. This is SentinelOne's newer unified Alerts concept (Purple/SDL-era), not the older Threats v2.1 REST endpoint. **Milestone 2 (ontology) and Milestone 3 (coverage matrix) must bind "threat count" intent to the real `search_alerts` tool, not an assumed threats-specific tool that doesn't exist here.**
- **`powerquery`'s own tool description instructs against hand-writing PowerQuery.** Verbatim: *"You should ALWAYS use the purple_ai() tool to generate PowerQueries for this tool based on natural language. It is very unlikely you know how to write PowerQueries yourself. If a user gives you a specific PowerQuery that wasn't generated by Purple AI, run it EXACTLY as sent."* This means the correct routing for a Deep-Visibility-shaped question is: `purple_ai(natural language question)` → take the PQ string it returns → `powerquery(that exact string, start_datetime, end_datetime)`, not composing PQ syntax directly. **This supersedes the field-name-based PowerQuery guidance added to `services/claude_service.py` in Phase 1 (PR #1) — that guidance should be revised once this ontology/routing work lands**, since it currently encourages the agent to hand-compose queries the tool's own author says it's unlikely to get right.
- **`powerquery` also documents that empty results are normal and must not be retried repeatedly** — directly matches the Task Execution Protocol's "empty is not clean" principle, and confirms it's the *tool's own author's* stance too, not just this project's convention.
- **`search_alerts` has a documented "how many" pattern**: *"If a user is asking a 'how many' type query, set the 'first' field to 1 - 'totalCount' is returned for any query."* This is the concrete mechanism behind the brief's own worked threat-count example (§8.1) and should be the exact retrieval path the coverage matrix binds "threat/alert count" to.

## Tool list by category

### PowerQuery / Deep Visibility

| Tool | Params (required in **bold**) | Notes |
|---|---|---|
| `powerquery` | **query**, **start_datetime**, **end_datetime** (ISO 8601, timezone offset mandatory) | Live-verified. Default 24h search window recommended; 5-minute query timeout. A malformed/legacy field name can close the whole MCP connection (observed in Phase 1 testing), not just error — treat query construction as high-stakes. Author's own guidance: don't hand-write the query, get it from `purple_ai` first. |
| `purple_ai` | **query** (natural language) | Generates/explains PowerQueries, answers security questions, cannot access live alerts (use alert tools for that), cannot run its own PQ output (pass to `powerquery`) or change config. Ask focused, descriptive questions (e.g. "Show me PowerShell processes that connected to external IPs"), not "generate a PowerQuery to..." |
| `get_timestamp_range` | none required; optional `reference_time`, `years/months/weeks/days/hours/minutes/seconds`, `direction` (`past`\|`future`, default `past`) | Live-verified. Returns `{current_time, offset_time}` ISO 8601 strings. Use this instead of hand-computing windows for `powerquery`. |
| `iso_to_unix_timestamp` | **iso_datetime** | Converts ISO 8601 → Unix ms (UTC). Required for datetime filters on the Alerts/Vulnerability/Misconfiguration/Inventory GraphQL APIs (they take Unix ms, not ISO strings). |

### Alerts (the real "threat count" source)

| Tool | Params | Notes |
|---|---|---|
| `get_alert` | **alert_id** | Full alert detail: severity, status, analystVerdict, storylineId, ticketId, assignee, etc. |
| `list_alerts` | `first` (1-100, default 10), `after` (cursor), `view_type` (`ALL`\|`ASSIGNED_TO_ME`\|`UNASSIGNED`\|`MY_TEAM`), `fields` (JSON array string) | Basic listing; no severity/status/time filtering — use `search_alerts` for that. |
| `search_alerts` | `filters` (JSON array of `{fieldId, filterType, value\|values, isNegated?}`), `first`, `after`, `view_type`, `fields` | **The threat-count recipe target.** Filter types: `string_equals`/`string_in`, `boolean_equals`/`boolean_in`, `long_equals`/`long_in`, `datetime_range` (needs Unix ms via `iso_to_unix_timestamp`), `fulltext`. Max 50 filters, 100 values/filter. `first=1` + read `totalCount` for count-only questions. |
| `get_alert_notes`, `get_alert_history`, `get_alert_investigation_report` | `alert_id` (+ pagination for history) | Notes/audit trail/Purple-AI auto-investigation report per alert. |

Not needed for the gap-closing intents (threat/alert count, host lookup, storyline pivot, agent health, CVE traversal) — CVE traversal uses the separate, keyless `cve_*` tools above.

## What's still unverified

Beyond `powerquery` and `get_timestamp_range`, none of these 33 tools have been exercised against real tenant data yet (schemas are real/live, call behavior is not). In particular: exact `storylineId`-based pivot behavior, real severity/status enum values as they actually appear in this tenant's data (the docstrings list the *possible* enum values, e.g. `CRITICAL/HIGH/MEDIUM/LOW/INFO/UNKNOWN`, but which ones actually occur here is a Milestone 1 discovery question), and whether `search_alerts`'s `storylineId` fulltext filter is sufficient for the brief's storyline-pivot procedure or needs `get_alert`'s `storylineId` field read first. These are exactly the open questions Milestone 1 (environment discovery) and Milestone 4 (recipe validation) exist to close.
